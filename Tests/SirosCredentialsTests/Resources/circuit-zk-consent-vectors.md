# circuit_zk consent test vectors

`circuit-zk-consent-vectors.json` maps what phase 1 of a `circuit_zk` request established to the
locale-free consent request the user is asked to approve. It is generated by
`tools/gen_circuit_zk_consent_vectors.py` (independent of the SDK code; `--check` verifies the
committed file) and is meant to be copied byte-for-byte into siros-sdk-swift, each SDK testing its own
builder against it. The SDK-owned wording is generated from these items and is not in the file.

## Format

`cases[]`: `name`, `today` (the date the age maths use), `input`, `expected`.

| `input` field | Meaning |
|---|---|
| `queries[]` | per query: `plan` (the planned functions: `id`, `handle`, `params`) and `credential` (`name`, `issuer`, each nullable) |
| `trust` | `entity_name`, `framework`, `identifier`, `intermediary_risk` (each may be absent) |
| `verified_client_id_display_name` | display name of the client id of a SIGNED request; null for an unsigned one |
| `attested_origin` | the platform-attested origin |
| `verifier_id`, `verifier_id_type` | what the wallet resolved; given only to queries with a pseudonym or legacy pseudonym |

`expected` is `{"refused": true}` (nothing can be asked: the request is refused) or `{"request": ...}` with
`verifier` (`label`, `trust_framework`, `trust_identifier`, `verifier_id`, `verifier_id_type`,
`intermediary_risk`), `entries[]` (`credential`, `items[]`) and `request_signed`.

Item kinds: `pseudonym` (`config`, `scope`, `remappable_by_issuer`, `cross_site`, `verifier_id`,
`verifier_context`), `claim` (`name`), `legacy_pseudonym` (`verifier_context`) and `predicate`: what the verifier
LEARNS about a claim (that it satisfies every condition), never its value.

`predicate`: `function`, `claim` (`path`; `label` is the credential's OWN display label for that path from
`credential.claims`, else null: a renderer falls back to the path, never an invented name), `value_type`
(`date`, `number`, `string`, `bool`), `conditions[]` (renderers choose their wording by `value_type` as well as `op`: a `date` claim has its own operator sentences, e.g. "on or after"; `age_form` wins for a function declared as an age; `op` one of `eq ne lt le gt ge in`, `values` as text of the
claim type) and `age_form` (null, or `between`/`at_least`/`at_most` computed from `today` for a function declared
as an age). The set of `circuit_zk` functions is open-ended, so predicate functions are DATA: `function_registry[]`
declares each one (`claim`: `{"path": [...]}` fixed or `{"param": "claim"}`; `value_type`; `comparisons`: param name
to op, in display order; optional `min_span`; optional `age_specialisation`). A function's params are a conjunction of
comparisons on one claim; any other param, a mistyped operand, a duplicated `in` member or no comparison refuses the
request. A function that is not in the registry (and is not a pseudonym or the legacy disclosure) refuses the
request: the wallet cannot say what it would disclose.

`precheck[]`: the local satisfiability check against a claim lookup (`found` with `type`/`text`, `absent`, or
`unsupported`). `expected` false = the credential definitely does not satisfy; true = it holds OR cannot be judged
(`unsupported` is skipped, never guessed; an absent claim is false).

`combined_predicate_bounds[]`: the cross-query privacy rule. The proofs of one request together reveal the
intersection of their predicates on a claim, so for plans answered with the SAME credential, per claim path and over
functions that DECLARE a `min_span`: lower = max `ge`, upper = min `le`; with both, the span (date: days inclusive;
number: `le - ge`) must reach the strictest declared `min_span` (`age_check`: 365 days). Functions that declare none
have no merge rule. An unreadable bound is not ok.

`verifier_id_shortening[]` pins the display shortening of a `verifier_id` (more than 40 code points keeps
the first and last 18 joined by U+2026). The value used for hashing is never altered.

The trust framework and `verifier_id_type` are in the model for hosts and tests; they never appear in the
default dialog text.

`combined_age_bounds[]` pins the check over queries answered with the SAME credential: the proofs of one
request together reveal the intersection of their age bounds (lower = latest `ge`, upper = earliest `le`),
which must still span at least 365 days (`upper - lower + 1`), else the request is refused. An unreadable
bound is not ok.

A query may carry `namespace` (the credential's doctype namespace, when known): the credential's claim metadata paths are
`[namespace, element]`, so a predicate on `score` is labelled by the entry `[namespace, "score"]`, never by another
namespace's `score`. An item param `source` (`{"path": [claim]}`, the rulebook example) is accepted when it names the
function's own claim, otherwise the request is refused.

## Age wording and empty requests

- A function declared `age_specialisation` renders as an age (`age_form`) ONLY when every condition of the request is a
  single `ge` or `le` bound. If it also declares `eq` (or any other comparison) and the request uses it, `age_form` is null
  and the generic wording states every comparison: the age wording says the exact birth date is not shared, which an `eq`
  contradicts (registry entry `age_with_eq`).
- A request with no query at all is refused (`expected: {"refused": true}`).
